## 0. 한 줄 정의

**K리그 2026 29개 구단 1,056명으로 내 스쿼드를 짜서, 브라우저에서 P2P 로 1:1 실시간 조작 축구 대전을 하는 게임.**

- 설치·가입·서버·DB 없음. GitHub Pages 정적 배포. 방을 만들고 P2P(WebRTC)로 붙는다.
- 카드형 온라인 축구 게임의 **형식**(카드·급여 상한·팀컬러·강화·포메이션·6분 경기·실시간 조작)을 따르되,
  **돈이 드는 것은 전부 뺀다** — BP·선수팩·이적시장·확률 강화·결제·광고 없음.
- 비상업. 엠블럼·사진·유니폼·타 게임 명칭을 쓰지 않는다. **제3자를 거명하는 고지 문구도 두지 않는다** (DECISIONS 3장 9).

### 3.2 게임패드 — 개발하지 않는다 (사용자 결정 2026-09-08)

**키보드 전용이다.** 게임패드는 백로그에도 두지 않는다 — 계획에서 뺐다. 첫 화면과 README 에 "PC 키보드 전용 · 게임패드 없음"으로 적는다.

### 3.3 조작 대상

- **공격**: 공을 가진 선수. 패스하면 받는 선수로 자동 전환.
- **수비**: 공에 가장 가까운 아군을 자동으로 잡는다. `L` 로 다음 선수. GK 는 조작하지 않는다 (v1).
- **자동 보조**: 패스는 스틱 방향 ±45° 콘 안에서 가장 좋은 동료에게 보정된다(없으면 ±90°). **슛은 언제나 골문을 겨눈다** (2026-09-10 개정) — 방향키의 위/아래 성분이 코너를 고르고, 안 누르면 골키퍼가 비운 코너. 골문 반대쪽으로 밀고 차면 오차만 ×1.6 커질 뿐 골문 밖으로 조준하지 않는다(예전엔 골문 방향 ±35° 밖이면 그 방향 그대로 나가 "아래 키 + 슛"이 골문을 통째로 벗어났다). **능력치 오차는 보정 뒤에 얹는다** (4.5·4.6).
- **방향 표시** (2026-09-10): 방향키를 누르고 있으면 조작 선수 앞 1.3 m 에 `›` 가 그 쪽을 가리킨다 — 공격은 노랑, 슛을 모으는 중엔 붉고 길어지며(파워), 수비는 흰색. 렌더 전용(`renderer3d.ts`)이라 결정론과 무관하다.

### 3.4 PC 전용 — 폰은 막는다 (사용자 결정 2026-09-08)

**터치 조작을 만들지 않는다.** 폰·태블릿으로 열면 로비 대신 "PC 에서 해 주세요" 안내만 보인다.

- 판정: `navigator.maxTouchPoints > 0` 이고 `matchMedia('(pointer: fine)')` 가 아니면, 또는 화면 폭 < 900px 이면 차단. 데스크톱 터치스크린 노트북(마우스도 있음)은 통과한다.
- 이유: 22명을 조작하는 데 스틱 하나 + 버튼 넷은 모자라고, **방장의 회선이 곧 방**(6.6)인데 폰 회선은 끊긴다. bedorage-duck 이 "폰에서는 방을 못 만들게" 막았던 것을 한 발 더 나간 것.
- 저사양 PC 는 설정에서 그림자를 끈다 (7.1).

## 4. 시뮬레이션 — 결정론

두 브라우저가 같은 입력으로 **완전히 같은 경기**를 내야 한다. `src/core/` 전체가 이 규칙 아래 있다.

### 4.1 좌표 · 시간

| 항목 | 값 |
|---|---|
| 피치 | 105 × 68 m. 원점은 센터 스팟. **홈이 +x 로 공격**, 후반은 sim 이 부호를 뒤집는다 |
| 단위 | m, `Float64`. 연산 순서를 고정하면 IEEE754 `+ − × ÷ sqrt` 는 엔진마다 같다 (`Math.sqrt` 는 정확 반올림) |
| 틱 | **60Hz** (`TICK_MS = 1000/60`). bedorage-duck `Ticker`(Web Worker) 그대로 — 탭이 뒤로 가도 돈다 |
| 각도 | 0..1023 (`fixedmath.ts`). `Math.sin/cos/atan2` 금지 |
| 골문 | 폭 7.32 · 높이 2.44 · 골라인 x = ±52.5. 공 중심이 골라인을 넘고 z < 2.44 면 골 |

### 4.2 공

- `(x, y, z)` + 속도 3D. 중력 9.81. 공기 저항은 **선형** `v -= v × 0.25 × dt` (결정론을 위해 제곱 저항을 쓰지 않는다). 지면 마찰 감속 4.0 m/s². 반발 계수 0.55 (z), 지면 접촉 시 수평 속도 ×0.85.
- 반경 0.11. 스핀·커브 없음 (v1).
- 골대·골포스트 충돌: 포스트 반경 0.06, 반발 0.7. 골네트는 공을 멈춘다.

### 4.3 선수 물리

| 항목 | 식 |
|---|---|
| 상태 | `pos, vel, facing(0..1023), stamina 0..1, action` — action ∈ {run, kick(예비 동작 틱), slide(슬라이딩 틱), fallen, gkDive} |
| 최고 속도 | `vmax = 6.0 + 3.2 × PAC/100` → 6.0 ~ 9.2 m/s. 스프린트 ×1.12. 볼 소유 시 `×(0.80 + 0.15 × DRI/100)` |

### 4.4 볼 소유 · 드리블 · 터치

- 공이 발 반경 **0.55 m** 안에 들어오면 소유 시도. 성공률 = `f(fir, tec, 공 속도, 공 높이)` — 낮고 느린 공은 거의 100%, 20 m/s 넘는 공은 `fir` 90 이라도 70%. 실패하면 공이 `rng` 로 튕긴다.
- 드리블 — **v1(단계 2 구현)은 붙임 모델**: 공을 발 앞에 붙이되 그 거리가 `DRI` 와 속도로 달라진다(서면 0.30 m, 전력으로 달리면 `0.65 + (1−DRI)×0.45` m). 멀리 붙을수록 상대의 태클 반경 안에 들어가 뺏기기 쉽다 — "밀어내는 터치" 대신 같은 효과를 싸게 얻는 방식이다. 터치 애니메이션이 필요해지면(단계 3 렌더) 밀어내기로 바꿀 수 있다.
- 페이스 컨트롤(`Ctrl`)은 붙임 거리 0.25 m · 속도 45% · 태클 확률 ×0.6.
- **잡기 판정은 공이 이번 틱에 지나온 선분까지의 거리**로 본다 — 20 m/s 공은 틱당 0.33 m 라 점 거리로는 발을 뚫고 지나간다(단계 2 에서 겪음). 받는 선수는 공 위치가 아니라 **요격 지점**(`interceptPoint`)으로 달린다.

### 4.5 패스

| 종류 | 목표 | 속도 | 오차 |
|---|---|---|---|
| 짧은 패스 `J` | 스틱 콘 안 동료 중 점수(거리·각도·마크 여유·전진성) 최고 | `clamp(8 + 0.9 × dist, 10, 24)` m/s, 홀드로 +20% | 각도 σ = `(1 − PAS/100) × 6°` + 압박 +2° + 퍼스트 타임 ×1.3 + 체력 저하 |
| 스루 `L` | 동료 **앞 공간** — 리드 = 동료 속도 × 도착 시간. `vis` 가 리드 정확도 | 짧은 패스 ×1.15 | σ ×1.4 |

### 4.6 슛

- 파워: 홀드 0~0.6 s → 속도 **16~30 m/s**. 파워가 클수록 z 성분이 커진다 (`fin` 높으면 낮게 깔린다).
- 방향: 3.3 의 보조 규칙. 골문 안 목표점은 스틱 좌우로 왼쪽 포스트 안·가운데·오른쪽 포스트 안 셋 중 하나.
- 오차 σ (도): `3.0 × (1.35 − SHO/100)` → SHO 90 = 1.35°, SHO 50 = 2.55°.
  가산 — 25 m 밖 `lon` 가중 · 각도가 좁을수록 · 압박(1.5 m 안 마크 ×1.5) · 약발 ×1.4 (`foot`) · 퍼스트 타임 ×1.3 · 헤더는 `hea` 로 별도.
- PK: `pen` 0.70 + `cmp` 0.30 (KM26 `penSkill` 그대로). 방향은 사람이 고르고 GK 는 AI.

### 4.7 골키퍼 (AI 전용)

- 위치: 골문 중심–공 직선 위, 골라인에서 **1.0~2.5 m** 앞 (`POS`). 1대1 이면 전진 (`cmd`). 사람이 **W**(수비)를 누르면 1.5초 동안 볼 소유자에게 돌진한다.
- 선방 (2026-09-10 개정 — "옆으로 찬 공이 손으로 빨려 들어간다" 제보): 잡기는 **실제로 손이 닿는 거리에서만** 난다 — 서서 0.8 m, 몸을 날리는 중 1.0 m. 다가오는 공의 **경로 위 가장 가까운 점**이 손 밖이면, 반응 지연 `0.25 − 0.15 × REF/100` s 뒤에 그 점을 향해 **몸을 날린다**(`ACT_DIVE`, 속도 `4.5 + 2.5 × HAN` m/s, 앞 12틱은 날고 뒤 12틱은 미끄러진다). 날아가는 동안 공이 손 안에 들어오면 잡기(`HAN`·거리·구속으로 성공률) 아니면 펀칭 → 리바운드 `rng`. 못 닿으면 들어간다 — 공은 **절대 순간이동하지 않는다** (`tests/feedback.test.ts` 가 한 틱 이동 0.6 m 이하를 본다).

### 4.12 결정론 규칙 (반드시 지킬 것)

bedorage-duck `DESIGN.md` 10장 그대로 + 축구용 두 개.

1. `Math.sin/cos/atan2/random/pow/exp`, `Date.now`, `performance.now` 금지. 삼각함수는 `fixedmath.ts`, 난수는 `rng.ts`.
2. `src/core/` 는 렌더·DOM·오디오를 import 하지 않는다.
3. 사람의 의사(프리셋 전환·교체 명령)는 반드시 `Input` 에 실어 보낸다. 렌더 쪽에서 상태를 바꾸지 않는다.
4. 부동소수 연산 순서를 바꾸지 않는다. 반복 순서도 상태의 일부다.
5. **22명 순회는 인덱스 순 고정.** 거리순 정렬이 필요하면 비교 함수의 동률을 선수 인덱스로 끊는다.
6. **`Array.prototype.sort` 에 동률을 남기지 않는다.** 스펙상 안정 정렬이지만 동률 처리를 믿지 않는다.

검증: `tests/determinism.test.ts` — 같은 시드로 두 번 돌려 60틱마다 해시 비교. 봇 vs 봇 90분 완주.

### 4.13 상태 해시 · 리싱크

60틱마다 `hashState`(22명 pos·vel·action, 공, 점수, 시계, rng 상태)를 게스트가 호스트에게 보낸다. 다르면 호스트가 스냅샷을 보내 되돌린다 (bedorage-duck `session.ts` 방식). 리싱크가 **한 판에 두 번 넘게** 나면 콘솔에 남기고 결과 화면에 "동기화 문제" 표시.

### 4.14 성능 예산

틱당 **0.5 ms 이하** (22명 AI 포함). `tests/perf.test.ts` 가 매번 잰다. 결정 주기 15틱 분산으로 AI 비용을 편다. 렌더(Three.js, 7.1)는 별도 예산 — 노트북 내장 GPU 60fps.

### 5.3 카드 OVR

포지션군(`pos`: GK/DF/MF/FW)별 6스탯 가중 평균 → 선형 보정 `a × raw + b`.

| 포지션 | PAC | SHO | PAS | DRI | DEF | PHY |
|---|---|---|---|---|---|---|
| FW | .20 | .35 | .10 | .20 | .05 | .10 |
| MF | .15 | .15 | .30 | .25 | .10 | .05 |
| DF | .15 | .05 | .10 | .10 | .40 | .20 |
| GK | DIV .25 · HAN .20 · KIC .10 · REF .25 · POS .15 · SPD .05 | | | | | |

보정 `a, b` 는 **도구가 데이터로 맞춘다** — 앵커 두 개: 리그 최상위 1% 가 **85**, 중앙값이 **63**. 손으로 정하지 않는다 (12장 원칙).

### 5.4 급여 (Salary)

| 카드 OVR | ~55 | 56–60 | 61–65 | 66–70 | 71–75 | 76–80 | 81–85 | 86+ |
|---|---|---|---|---|---|---|---|---|
| 급여 | 3 | 4 | 5 | 7 | 9 | 12 | 16 | 21 |

**상한(CAP)** 은 18명 합. 값은 `tools/calibrate.py` 가 정한다 — 조건 둘:

1. 리그 최상위 18명(포지션 맞춰)의 급여 합 **× 0.70** 근처 → 올스타 팀 불가.
2. **29개 구단 어느 곳이든(K리그2 포함) 자기 선수 18명으로 짠 팀은 상한 안에 든다** → 순수 팀컬러 팀은 언제나 가능 (사용자 결정 2026-09-08 — K리그2 까지).

두 조건이 부딪히면 2 가 우선이고, 1 의 배수를 낮춘다. 조건 2 를 실제로 조이는 것은 급여 합이 가장 큰 구단(K리그1 상위)이므로, K리그2 를 넣어도 상한은 같을 가능성이 높다 — **도구가 29개 전부 세어 확인한다.** (초기 어림 상한 ≈ 180. **실측으로 다시 잡는다.**)

### 5.5 강화 — 예산제

- 스쿼드 예산 **24 포인트**, 카드당 **최대 +5**. 확률·비용 없음.
- **+1 = 원본 능력치 40종(GK 11종) 전부 +1** (상한 99) → 6스탯 +1, 카드 OVR +1.
- 급여는 강화와 무관. 제약은 예산뿐.
- 검증: `Σ enh ≤ 24`, `each ≤ 5`. 어기면 스쿼드를 받지 않는다.

### 5.6 팀컬러

선발 11명 중 **같은 구단** 수(최다 구단 하나만):

| 인원 | 5 | 7 | 9 | 11 |
|---|---|---|---|---|
| 보너스 | 전원 +1 | +2 | +3 | +4 |

능력치 40종 전부에 더한다(강화와 같은 방식, 상한 99). 벤치는 세지 않는다.

### 5.7 포지션 적합도

KM26 `posFam[슬롯]`(0~100)을 그대로 쓴다. 표시는 5색.

| 능숙도 | 100 | 70–99 | 45–69 | 20–44 | <20 |
|---|---|---|---|---|---|
| 색 | 초록 | 연두 | 노랑 | 주황 | 빨강 |

시뮬 페널티는 KM26 `applyFamiliarity` 계수를 우리 스킬에 옮긴다 — 무겁게(×`FAM_PEN_HEAVY 0.58` 까지): AI 판단 오차·앵커 이탈·패스·마크. 가볍게(0.26): 슛·드리블·퍼스트 터치. 라인 이탈 한 칸당 −13%. **GK 를 필드에 / 필드 선수를 골문에 −42%.**

## 6. 네트워크 — bedorage-duck 을 옮긴다

### 6.1 구조

- **시그널링**: Trystero + 공개 Nostr 릴레이. 내가 운영하는 서버 없음. STUN 은 Google 공개, **TURN 없음** (10장).
- **공용 로비 방**: 접속자 전원. 방장이 2초마다 방 정보를 방송, 7초 소식 없으면 목록에서 지운다.
- **게임 방**: 6자 코드, **정원 2**. 방장 = 홈 = 플레이어 0. 코드는 내부 식별자 — 들어가는 길은 방 목록뿐 (초대 링크 없음, bedorage-duck 2026-09-05 결정 그대로).
- `APP_ID = 'klo26-v1'` — 프로토콜이 바뀌면 올린다. 개발 서버와 배포본이 같은 릴레이를 쓰므로 목록이 섞인다 — 개발 중엔 `APP_ID` 에 `-dev` 를 붙인다.

### 6.2 방 정보 (목록에 보이는 것)

방장 닉네임 · 팀컬러 최다 구단(짧은 이름 + 색) · 스쿼드 OVR(선발 평균) · 경기 시간 · 오프사이드 · 상태(open/full/playing).

### 6.3 대기실 절차

```
게스트 → 방장  hello { 닉네임, 스쿼드 코드 }
방장          검증 (5.8) → 실패면 reject { why } → 게스트를 돌려보낸다
방장 → 게스트  room  { 방장 닉네임·스쿼드 코드, 옵션(시간·오프사이드), 양쪽 ready }
양쪽          상대 스쿼드 미리보기 (포메이션·OVR·팀컬러) → ready
방장 → 게스트  start { seed, 옵션, 코드A, 코드B, delay }
```

`seed` 는 4.11 규칙으로 **양쪽이 각자 계산해 같은지 확인**한다 — 방장이 보낸 값과 다르면 시작하지 않는다.

### 6.4 락스텝

- 입력 **6바이트** `mx i8 · my i8 · buttons u16 · a u8 · b u8` — buttons 는 **키 그대로**: S · W · A · D · E · Ctrl · Space · C · Q · Z · `]` · `[` · SUB (13비트). 공격/수비 뜻은 시뮬이 가른다(3.1). `a, b` 는 교체 명령의 (나가는 선발 인덱스, 들어오는 벤치 인덱스).
- 틱 `t` 입력을 `t + delay`(2~6, RTT 로) 에 배정. 최근 8틱 중복 전송. 둘 다의 입력이 있는 틱만 진행(스톨). `Lockstep` 클래스는 bedorage-duck 것을 2인으로 쓴다 (봇 자리·난입 경로는 안 쓴다).
- **12초 무응답 = 나감.** 방장이 나가면 경기 종료 (2장 "상대가 나가면").
- 재접속·난입 **없음** (v1). 축구는 한쪽이 비면 성립하지 않는다.

### 6.5 해시 · 리싱크

4.13. 방장 스냅샷이 정본.

### 6.6 한계 (정직하게)

- **치트 방지 불가.** 권위 서버가 없다. 방장이 자기 sim 을 고치면 리싱크가 그걸 정본으로 만든다. 친구 대전용.
- 대칭 NAT·회사망에서는 연결이 안 될 수 있다. TURN 없음 → "폰 핫스팟으로 재시도" 안내가 최종.
- 가장 느린 회선에 둘 다 맞춰진다. 방장은 유선 PC 가 안전하다는 것을 계속 말해 준다.

### 6.7 혼자 하기

봇(4.10) 이 상대 팀 22명을 굴린다. 락스텝 없이 같은 `sim` 을 돈다. 방 지키기(자동 방장)는 bedorage-duck `tools/rooms.mjs` 를 옮겨 온다 — 필요해지면.

## 7. 화면 · 렌더

### 7.1 시점 — Three.js 방송 카메라 (사용자 결정 2026-09-08)

사이드라인 위 방송 카메라 시점. bedorage-duck 이 2D 에서 Three.js 로 갈아탈 때 쓴 방식 — **프리미티브 조립 캐릭터 + 툰 셰이딩, 시뮬은 한 줄도 안 바꾼다** — 을 그대로 쓰되 카메라만 쿼터뷰에서 방송 시점으로 바꾼다.

**카메라**

- 원근 카메라 FOV 32°. 사이드라인 바깥 **38 m · 높이 30 m**, 시선을 카메라 쪽으로 6 m 당겨 아래로 약 25° (단계 3 에서 26 m·35° 를 이렇게 바꿨다 — 관중석이 화면 위 1/3 을 먹어서). x 는 공을 따라가되 진행 방향으로 **리드 6 m**, 골문에 가까워질수록 줌인(FOV 32 → 26). 수치는 `src/render3d/camera.ts` 한 곳에.
- 따라감은 **렌더 전용 보간**(sim 과 무관). 후반에도 카메라는 그대로 — 방송처럼 진영이 바뀌어 보인다.
- PC 전용(3.4)이라 화면 비율은 16:9~16:10 만 본다. 창이 좁으면 좌우를 자르지 않고 FOV 를 키운다.

**선수 — 귀여운 찰흙**

- 프리미티브 조립: 머리 = 구(대두, 머리:몸 ≈ 1:2.2), 몸통 = 캡슐, 팔·다리 = 짧은 캡슐, 신발 = 납작 구. **`MeshToonMaterial`(3단 그라디언트) + 무광** → 찰흙 느낌. 외곽선 없음.
- 동작: 걷기/달리기 다리 스윙(속도 비례) · 킥(다리 앞으로 + 상체 기울임) · 슬라이딩(눕기) · GK 다이브 · 넘어짐 · 피격 스쿼시. 전부 코드 애니메이션, 외부 모델·리깅 없음.
- **키 반영**: 데이터 `h`(cm) → 모델 높이 배율 **`h / 180`** (158 cm → 0.88, 197 cm → 1.09). 몸무게 `w` → 몸통·팔다리 굵기 `sqrt(w / 75) × 0.8` (2026-09-10 "조금 더 마르게" — `SLIM 0.8`, 머리는 그대로 대두). 4.3 의 헤더·몸싸움 보정(`bodyFx`)이 같은 값을 보므로 **보이는 대로 논다** — 큰 선수가 커 보이고 헤더도 잘한다.
- **피부색: 반영하지 않는다.** 데이터에 없다. 이름·국적으로 추정하면 실존 인물에 대한 억측이 된다. 찰흙색 한 가지(연한 황토). 데이터가 생기면 다시 본다 (13장).
- **생김새: 닮게 그리지 않는다.** 점 눈 둘 + 작은 입. 머리 모양 4종(짧은·덮은·묶은·민머리)을 **선수 id 해시로** 돌려 배정 — 실존 인물과 무관하다. bedorage-duck 의 얼굴 캐리커처 경로는 쓰지 않는다.
- 유니폼: 상의 `col`, 소매·양말 `col2`, 등번호는 캔버스 텍스처. 두 팀 색이 가까우면(색 거리 임계 아래) 원정은 흰 상의. 실제 유니폼 디자인은 쓰지 않는다.

**피치 · 조명**

- 평면 + 잔디 줄무늬 텍스처(코드 생성) · 라인·박스·아크(데칼) · 골대(실린더) · 골네트(반투명 격자). 광고판 없음. 관중석은 낮은 박스 띠 + 색 점(코드).
- 방향광 1 + 그림자맵 + 앰비언트. 저사양 PC 는 설정에서 그림자 끄기 + 해상도 0.75.

**판독성 — 3D 라서 더 챙길 것** (멀리 있는 선수가 작다)

- 조작 중인 선수: 머리 위 화살표 + 이름표 빌보드 + 발밑 링.
- 공 그림자 데칼(높이 z 에 따라 벌어진다).
- **레이더 필수**(2D 였으면 선택) — 전체 피치 축소, 22명 점, 공.
- 오프사이드 라인 데칼(옵션) · 패스 콘 데칼(누르고 있을 때) · 슛 파워 게이지(HUD).

**성능 · 결정론**

- 22명 × 약 300 삼각형. 노트북 내장 GPU 60fps 목표. 렌더는 `prev/curr` 보간만 하고 `src/core` 는 Three 를 모른다.

## 10. 비용 원칙 · 쓰지 않는 것

### 10.1 비용 (bedorage-duck 15장 그대로)

**카드 등록이 필요한 서비스는 무료 티어라도 쓰지 않는다.** GitHub Pages · Google Fonts · 공개 Nostr 릴레이 · 무료 STUN 만. TURN 전부 배제. 광고·결제·후원 없음.

### 10.2 쓰지 않는 것 — 고지 대신 안 쓰는 것으로 답한다

**제3자를 거명하는 고지 문구를 두지 않는다** (사용자 결정 2026-09-08, DECISIONS 3장 9). 첫 화면·README·소스 어디에도 "~와 무관하다" 류의 문장을 쓰지 않는다. 대신 아래를 지킨다.

- 구단 엠블럼·공식 로고·유니폼 디자인·선수 사진을 쓰지 않는다. 구단은 **색 두 개와 이름**으로만.
- 선수 모델은 **닮게 그리지 않는다**(7.1). 머리 모양은 id 해시로 무작위이고 피부색은 한 가지다.
- 타 게임의 이름·에셋·코드·UI 를 쓰지 않는다.
- 선수 이름: **보호명** (사용자 결정 2026-09-08). KM26 `fictName` 규칙을 그대로 — 국내 선수는 성씨 치환(김→금 · 이→리 · 박→백 · 정→종 · 최→체 …, 표에 없으면 초성 한 칸), 외국인은 첫 글자 초성 한 칸(마테우스→바테우스), 바뀐 이름이 다른 실존 선수와 겹치면 초성 한 칸 더.
  **`build_cards.py` 가 빌드 단계에서 적용하므로 저장소·화면·코드 어디에도 실명이 남지 않는다.** 엔진·UI 는 id 로만 참조한다. 단계 1 검토 기준에 "원본 이름 전부와 대조해 저장소에 실명 0건"을 넣는다.
- 그래픽·소리는 전부 코드로 생성한다. 외부 에셋 없음. 폰트는 Google Fonts (OFL).
- 데이터 사용 허락은 [PREP.md](PREP.md) A-1 에서 재확인한다. 확인 기록은 저장소 밖(사용자 보관)에 둔다.

## 12. 밸런스 · 검증 방법론

KLD26 과 KMD26 에서 얻은 규칙을 그대로 쓴다.

1. **추정은 숫자로 판정한다.** "느낌"으로 계수를 만지지 않는다. 문턱을 못 넘으면 멈추는 것이 결론이다.
2. **적은 표본으로 판정하지 않는다.** 봇전은 시드 500판 이상. "3판 보고 결론"으로 두 번 틀렸다.
3. **슬라이더가 연결됐는지는 지문으로 본다.** 같은 시드로 값만 바꿔 두 판 돌려 결과 지문이 같으면 엔진이 그 값을 안 읽는 것이다 (KMD26 이 "패스 길이 미반영"을 이걸로 잡았다). 4종 전부 + 강화 + 팀컬러 + 능숙도.
4. **짝 비교 + 부호검정.** 같은 시드로 낮은 값·높은 값을 나란히 돌리고, 그 손잡이가 직접 건드리는 지표(압박 → 태클 수, 라인 → 오프사이드 수)가 기대한 쪽으로 움직인 쌍의 비율을 센다. 16쌍이면 판정이 선다.

| 검증 | 합격 기준 |
|---|---|
| 봇 vs 봇 500판 (보통) | 평균 총득점 **2.5~3.5 / 6분**, 0:0 비율 < 25%, 한 팀 5골 이상 < 3% |
| 홈/원정 대칭 | 같은 스쿼드끼리 500판 → 홈 승률 47~53% |
| 팀컬러 +4 vs 0 | 승률 차 **+8~15%p** (있어야 하지만 지배적이면 안 된다) |
| 강화 24 vs 0 | 승률 차 +8~15%p |
| 슬라이더 극단 | 중앙값 대비 승률 ±8%p 이내 |
| 능숙도 빨강 11명 vs 초록 11명 | 초록 승률 ≥ 70% |
| 같은 시드 100회 | 해시 100% 일치 |
| 사람 체감 | **오픈 베타에서 카페 댓글로.** 봇 계측은 참고일 뿐이다 (bedorage-duck 12.1) |
