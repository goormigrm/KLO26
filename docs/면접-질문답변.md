# 개리그 온라인 2026 — 개발자 면접 질문·답변

> 이 프로젝트를 면접에서 설명한다고 가정하고 쓴 문서입니다. 왼쪽은 면접관이 물어볼 만한 질문, 오른쪽은 답변입니다.
> 숫자는 전부 저장소에 남아 있는 실측값이고, 근거 파일을 함께 적었습니다.

## 0. 30초 소개

> **"이 프로젝트를 한 문장으로 소개해 주세요."**

K리그 2026 선수 1,056명으로 스쿼드를 짜서, **브라우저에서 서버 없이 1:1 실시간 조작 축구**를 하는 웹 게임입니다.
설치·가입·서버가 없고, 두 사람의 브라우저가 WebRTC로 직접 붙어 **결정론 락스텝**으로 같은 경기를 돌립니다.
TypeScript로 시뮬레이션 코어를 직접 짰고, 물리·AI·축구 규칙·밸런스 계측까지 전부 코드 안에 있습니다.

> **"1분 버전으로는요?"**

세 덩어리입니다.

1. **결정론 시뮬 코어** — 60Hz 고정 틱, 룩업 테이블 삼각함수, 시드 난수. 같은 입력이면 어느 브라우저에서도 바이트 단위로 같은 결과가 나옵니다.
2. **P2P 락스텝 네트워크** — 서버가 없으니 상태를 동기화하지 않고 **입력만** 주고받습니다. 60틱마다 상태 해시를 대조해 어긋나면 스냅샷으로 되돌립니다.
3. **밸런스를 숫자로 판정하는 도구 모음** — "능력치가 경기에 반영되나", "홈/원정이 공정한가" 같은 질문을 느낌이 아니라 수백~수천 판 A/B로 답했습니다.

## 1. 기술 스택

> **"어떤 언어와 도구를 썼습니까?"**

| 영역 | 선택 | 이유 |
|---|---|---|
| 언어 | **TypeScript** (strict) | 시뮬 상태가 20개 넘는 타입으로 얽혀 있어 타입이 없으면 못 버팁니다. `any` 없이 `tsc --noEmit` 통과를 빌드 조건으로 걸었습니다 |
| 빌드 | **Vite** | 개발 서버 HMR과 정적 번들 하나면 충분합니다. 백엔드가 없으니 SSR·프레임워크가 필요 없습니다 |
| 렌더 | **Three.js** | 3D 방송 카메라가 목표였고, 캔버스 2D로는 원근·그림자·관중석을 못 만듭니다 |
| 네트워크 | **Trystero** (WebRTC + Nostr 시그널링) | 서버 없이 P2P를 붙이려면 시그널링이 필요한데, 공개 릴레이를 쓰면 **내 서버가 0대**가 됩니다 |
| 테스트 | **Vitest** | 26개 파일 167개. 결정론·성능·규칙·경제·네트워크 배선까지 |
| 데이터 추출 | **Python** + **Go(goja)** | 원본 게임의 선수 생성기를 **옮겨 적지 않고 그대로 실행**하려고 (아래 5장) |
| UI | **바닐라 DOM + CSS** | 화면이 6개뿐이고 상태가 시뮬 안에 있어서 프레임워크가 얻을 게 없었습니다 |
| 배포 | **GitHub Pages + Actions** | 정적 파일이라 푸시하면 끝. 비용 0원 |

> **"프레임워크(React 등)를 안 쓴 이유는요?"**

이 앱의 진짜 상태는 **DOM이 아니라 시뮬레이션 상태**입니다. 60Hz로 바뀌는 22명의 좌표를 가상 DOM으로 그릴 이유가 없고,
실제로 화면에 남는 DOM은 전광판·배너·메뉴 정도입니다. 대신 **경계를 규칙으로 못 박았습니다** — `src/core/` 는 DOM·렌더·오디오를 import 하지 않습니다.
그 규칙 덕분에 코어를 Node에서 그대로 돌려 수천 판 계측을 할 수 있었습니다(이게 이 프로젝트에서 제일 값어치가 컸습니다).

## 2. 아키텍처

> **"전체 구조를 그려 주세요."**

```
src/core/     결정론 시뮬 (DOM·렌더·오디오를 모른다)
  state.ts    상수·타입·GameState
  sim.ts      createState / step(한 틱) / hashState
  physics.ts  공·선수 이동, 충돌, 골라인 판정
  ball.ts     소유·태클·패스·슛·골키퍼·파울 판정
  rules.ts    시계·하프·킥오프·세트피스·카드·교체
  ai.ts       22명 AI (자리·압박·마크·침투)
  fixedmath.ts 결정론 삼각함수 / rng.ts 시드 난수
src/render3d/ Three.js 렌더 (prev/curr 보간만, 시뮬을 안 바꾼다)
src/net/      Trystero 로비·방·락스텝
src/cards/    카드·스쿼드·급여·팀워크·스쿼드 코드
src/ui/       로비·스쿼드·대기실·설정
tools/        밸런스 계측 도구 15종 (Node에서 코어만 돌린다)
tests/        Vitest 167개
```

> **"렌더와 시뮬을 나눈 기준이 뭔가요?"**

**"두 브라우저가 같아야 하는가"** 하나입니다.

- 같아야 하는 것 → 시뮬: 골 세레머니(모임·건너뛰기 동의)는 양쪽이 같은 상태여야 하므로 `core/rules.ts` 안에 있습니다.
- 달라도 되는 것 → 렌더: 골 리플레이는 **렌더 전용 링 버퍼**입니다. 지나간 프레임의 포즈를 따로 저장해 느리게 다시 그릴 뿐이라, 시뮬은 그동안 평소대로 돕니다. 락스텝·해시를 전혀 건드리지 않습니다.

이 기준을 세워 두니 "연출을 추가하면 동기화가 깨지나?"를 매번 고민할 필요가 없어졌습니다.

## 3. 결정론과 네트워크

> **"서버 없이 어떻게 두 사람이 같은 경기를 봅니까?"**

**결정론 락스텝**입니다. 상태를 보내지 않고 **입력(6바이트)만** 보냅니다.

- 60Hz 고정 틱. `step(state, [입력A, 입력B])` 가 순수 함수처럼 동작합니다.
- 입력은 3틱 뒤에 적용하기로 약속하고(왕복 시간에 따라 조정), 그 사이에 상대 입력이 도착합니다.
- 60틱마다 `hashState()`(FNV-1a)를 게스트가 방장에게 보내 대조하고, 어긋나면 방장이 스냅샷을 보내 되돌립니다.

> **"결정론을 어떻게 보장했습니까? 부동소수점이 문제 아닌가요?"**

네 가지를 규칙으로 못 박고 테스트로 지킵니다(`DESIGN 4.12`).

1. **삼각함수 금지** — `Math.sin/cos/atan2` 대신 1024단계 룩업 테이블(`fixedmath.ts`)을 씁니다. 테이블 값은 1/65536 단위로 반올림해 엔진별 ulp 차이를 없앴습니다. `atan2`는 테이블 이진 탐색으로 구현했습니다.
2. **난수는 시드 하나** — mulberry32. 시드는 두 스쿼드 코드와 방 코드의 해시라 **누구도 고를 수 없습니다**. 봇 AI는 별도 스트림을 써서, 사람 대전에서 봇이 없어도 난수 흐름이 같습니다.
3. **연산 순서를 바꾸지 않는다** — 반복 순서도 상태의 일부입니다. 거리순 정렬이 필요하면 동률을 선수 인덱스로 끊습니다.
4. **`Date.now`·`performance.now` 금지** — 시간은 틱 수로만 셉니다.

검증은 `tests/determinism.test.ts` 가 같은 시드로 두 번 돌려 60틱마다의 해시를 전부 비교합니다. 실제 두 탭 대전에서도 1500틱까지 해시가 완전히 일치했고 리싱크는 0이었습니다.

> **"WebRTC 연결이 안 될 때는요?"**

정직하게 한계를 적었습니다. TURN 서버를 두지 않아서(서버 0대 원칙) **대칭 NAT 환경에서는 안 붙습니다**.
안내 문구로 "회사·학교 네트워크에서 잘 막히니 한쪽을 폰 핫스팟에 물려 보세요"를 띄웁니다.
숨기는 것보다 조건을 알려 주는 편이 사용자에게 낫다고 판단했습니다.

> **"최근에 네트워크 쪽에서 바꾼 게 있나요?"**

방 만들기 흐름을 바꿨습니다. 예전에는 방을 만드는 순간 대기실로 들어가 **스쿼드가 그때 확정**됐는데,
기다리는 동안 스쿼드를 고칠 수 없다는 불만이 있었습니다. 그래서

- 방 만들기는 **연결만 열고**(`net/hostroom.ts`) 로비에 남습니다. 연결을 화면 밖(`main.ts`)에 두어 로비 ↔ 스쿼드 화면을 오가도 살아 있습니다.
- 상대가 들어오면 알림이 떠서 "저장하고 대기실로 / 조금 더 준비하기"를 고릅니다.
- **스쿼드는 준비 버튼을 누를 때 확정**됩니다. 대기실이 스쿼드 값이 아니라 `getSquad()` 함수를 받고, 누르는 순간 규칙 검사 후 코드로 굳힙니다.

여기서 한 번 걸린 것이, 대기실이 기존 연결을 이어받은 뒤에도 **`HostRoom`의 콜백이 계속 살아 있어** 빈 스쿼드 코드를 덮어쓴 문제였습니다.
`openRoom`이 콜백을 배열로 쌓는 구조라서, 넘긴 뒤에는 플래그로 무시하게 했습니다.

## 4. 게임플레이 구현

> **"축구 규칙은 어디까지 구현했습니까?"**

오프사이드(공을 찬 순간의 위치 + **관여해야 반칙**), 백패스 룰, 두 번 터치, 골키퍼 차징, 스로인(손·직접 골 불인정),
프리킥·PK·코너·골킥, 경고/퇴장, 추가시간(공이 죽어 있던 시간만큼 계산), 교체(기회 3번·최대 5명·하프타임 무료), 심판 3명입니다.

> **"AI는 어떻게 만들었습니까? 머신러닝인가요?"**

아닙니다. **효용 점수 기반 행동 선택 + 자리(앵커) 모델**입니다.

- **자리**: 포메이션 슬롯 좌표를 피치로 펴고, 공 위치로 끌어당기고(x 0.40 · y 0.30), 전술 슬라이더(라인·폭·멘탈리티)로 옮깁니다.
- **공을 가졌을 때**: 슛/패스/드리블/클리어의 효용을 점수로 매겨 최대를 고릅니다. 패스 점수는 전진 이득·상대와의 거리·패스 길이 막힘·시야 능력치로 만듭니다.
- **공이 없을 때**: 압박 1순위, 커버 2순위, 나머지는 골사이드 대인 마크. 침투 러닝은 소유자보다 앞이고 앞이 비었을 때 오프사이드 라인 직전까지 달립니다.
- 성능을 위해 **결정 주기는 15틱**이고 선수마다 오프셋을 줘 한 틱에 두 명만 다시 결정합니다.

> **"능력치가 실제로 경기에 영향을 준다는 걸 어떻게 확인했습니까?"**

이 질문이 이 프로젝트에서 제일 중요한 방법론이었습니다. **코드를 읽어서 답하지 않고 A/B로 쟀습니다.**

`tools/attrcheck.ts` 가 같은 스쿼드 두 벌을 만들어 한쪽 능력치 묶음만 92, 다른 쪽은 38로 바꾸고,
홈/원정을 교대하며 200경기를 돌려 승률을 봅니다. **대조군은 정확히 50%** 가 나와야 합니다.

처음 돌렸을 때 결과가 이랬습니다.

| 묶음 | 승률 | 판정 |
|---|---|---|
| 속도 | 89.8% | 지배적 |
| 태클·마크·패스·골키퍼 | 49~51% | **경기에 안 닿는다** |

계수가 코드에 분명히 있는데도 승률이 50%였습니다. 이유는 **빈도**였습니다 — 태클 성공식을 아무리 키워도 판당 태클이 5번이면 승률이 안 움직입니다.
그래서 성공률이 아니라 **기회(닿는 거리)** 를 늘렸고, 패스는 각도가 아니라 **세기 오차**가 죽는 원인이라 거기에 능력치를 걸었습니다. 결과는 56~68%로 올라왔습니다.

> **"속도가 지배적이었다면 어떻게 잡았습니까?"**

폭만 줄이는 건 답이 아니었습니다(89.8% → 81%, 여전히 지배적).
**"속도가 어디서 이기는지"** 를 막아야 했고, 실제 축구의 제동 장치를 옮겨 왔습니다.

- 공을 몰고는 전력 질주 속도가 안 나온다(드리블 상한)
- 전력으로 몰면 터치가 길어져 뺏기기 쉽다
- 달리면서 찬 슛은 오차가 커진다
- 체력이 닳으면 느려진다

넷을 다 넣고서야 72%로 내려왔습니다. **"너무 세다"는 폭을 줄이는 것만으로 안 끝난다**가 여기서 얻은 교훈입니다.

## 5. 데이터 파이프라인

> **"선수 데이터는 어디서 왔고 어떻게 처리했습니까?"**

원작자 허락을 받은 같은 제작자의 다른 게임(개리그 매니저)의 원본 HTML에서 가져왔습니다. 여기 재미있는 문제가 있었습니다.

**원본에는 능력치가 저장돼 있지 않습니다.** 들어 있는 건 표 세 개(1부 명단·2부 팀 수준·실제 등록 명단 1,056명)뿐이고,
세부 능력치 40여 종은 `mkPlayer()` 함수가 OVR·포지션·나이·키로 **만들어 냅니다**.

그 함수를 다른 언어로 옮겨 적으면 반드시 어딘가 어긋나고, 값이 달라지면 "같은 선수"가 아니게 됩니다.
그래서 옮겨 적지 않고 **원본 함수를 그대로 뽑아 한 번 실행**했습니다.

```
index.html ──extract_data.py──> gen.js ──go run (goja)──> data/*.json ──build_cards.py──> cards.json
            (의존성 폐포 + 시드 고정)   (원본 JS 실행)        (보호명·컬럼 포맷)
```

- **Python**: 최상위 선언을 파싱해 필요한 함수만 따라가는 **의존성 폐포**를 만들고, `Math.random()` 17곳을 시드 난수로 치환합니다.
- **Go(goja)**: 그 JS를 그대로 실행해 JSON으로 떨굽니다. 시드를 고정했으니 몇 번 돌려도 같은 값이 나옵니다.
- **보호명**: 저장소에 실명을 한 건도 남기지 않습니다. 한국 선수는 성씨를 다른 실재 성씨로 치환(김→구, 이→여), 외국 선수는 첫 글자 초성을 밉니다. 같은 구단 안에서 겹치거나 **다른 실존 선수 이름이 되어 버리면** 마지막 글자 초성을 밀어 떼어 놓고, 도구가 끝에서 "실명 0건"을 직접 확인합니다.

> **"원본이 갱신되면 어떻게 합니까?"**

업스트림은 파일이 하나뿐이라 커밋 수로는 갱신 여부를 알 수 없습니다(같은 파일을 지웠다 다시 올립니다).
그래서 **blob 해시로 판정**합니다. 실제로 최근 확인 때 커밋 8개가 쌓였지만 blob이 같아 반영할 게 없었고,
확실히 하려고 파이프라인을 끝까지 돌려 결과 파일의 md5가 같은지까지 봤습니다.

명단이 바뀌면 `POOL_HASH`가 바뀌어 **저장된 스쿼드가 전부 무효**가 됩니다. 이건 버그가 아니라 의도한 장치입니다 —
스쿼드는 선수 id만 들고 있어서, 명단이 바뀌면 같은 id가 딴 선수를 가리킵니다(실제로 "골키퍼 자리에 공격수" 사고가 났었습니다).

## 6. 밸런스와 검증 방법론

> **"밸런스는 어떻게 맞췄습니까?"**

규칙 네 개를 정해 두고 지켰습니다.

1. **추정은 숫자로 판정한다.** 느낌으로 계수를 만지지 않습니다.
2. **적은 표본으로 판정하지 않는다.** 봇전은 시드 500판 이상.
3. **슬라이더가 연결됐는지는 지문으로 본다.** 같은 시드로 값만 바꿔 돌렸는데 결과가 같으면 엔진이 그 값을 안 읽는 것입니다.
4. **짝 비교 + 부호검정.** 같은 시드로 낮은 값/높은 값을 나란히 돌려, 그 손잡이가 직접 건드리는 지표가 기대한 쪽으로 움직인 쌍의 비율을 셉니다.

이걸 위해 계측 도구를 15개 만들었습니다(`verify`·`asym`·`attrcheck`·`tactics`·`economy`·`shots`·`stamina` 등).
전부 **코어만 Node에서 돌립니다** — 렌더 없이 수천 판을 몇 분에 끝낼 수 있는 건 `src/core/`가 DOM을 모르기 때문입니다.

> **"가장 어려웠던 버그 하나를 자세히 설명해 주세요."**

**홈 팀이 계속 지는 문제**입니다. 면접에서 이야기한다면 이 사례를 고르겠습니다.

**증상.** 완전히 같은 스쿼드끼리 붙이는 대칭 테스트에서 홈 승률이 41%로 나왔습니다. 대칭이면 50%여야 합니다.

**첫 번째 함정 — 표본.** 예전에 같은 테스트를 100판 돌려 51.7%가 나와 "닫힌" 문제였습니다. 다시 재 보니 200판 노이즈가 ±4%p였고,
같은 코드가 41%·45.6%·48.3%·51.7%로 나왔습니다. **200판으로는 3%p 편향을 못 봅니다.** 그래서 이후 판정은 전부 2,000판으로 했습니다.

**두 번째 함정 — 엉뚱한 곳 찾기.** 처음엔 좌표 버그를 의심해 "진영을 안 곱한 절대 x 조건"을 grep으로 뒤졌습니다. 못 찾았습니다.
방향을 바꿔 **원인을 축으로 갈랐습니다**. 진단 도구를 만들어 같은 경기를 세 가지로 변형했습니다.

| 변형 | 결과 |
|---|---|
| 진영만 뒤집기 | 여전히 팀 1 승 |
| 킥오프 팀만 바꾸기 | 여전히 팀 1 승 |
| 둘 다 | 여전히 팀 1 승 |

좌표도 킥오프도 아니고 **팀 번호(0/1)에 붙은 편향**이라는 뜻이었습니다. 확인 사살로 선수 순회를 거꾸로 돌렸더니 같은 시드에서 45.6% → 50.3%로 뒤집혔습니다.

**원인.** `step()` 안에 팀 번호에 붙은 순서가 **세 개** 있었습니다.

1. AI 결정이 이동 루프 **안**에 있어서, 팀 1(11~21번)은 팀 0이 이미 이 틱만큼 움직인 뒤에 판단했습니다 — 한 틱 앞선 정보로 요격·마크를 잡은 셈입니다.
2. 팀 0이 늘 먼저 결정해서, 팀 0의 패스는 같은 틱에 팀 1에 들키고 팀 1의 패스는 한 틱 늦게 들켰습니다.
3. 결정 주기(15틱) 오프셋이 `idx`라서, 마주 보는 두 선수의 반응 시차가 팀마다 달랐습니다(11 ≢ 0 mod 15).

**해결.** `step()`을 **결정 22명 → 이동 22명** 두 단계로 나누고, 결정 순서는 **공을 가진 팀부터**, 주기 오프셋은 **자리 번호(idx % 11)** 로 바꿨습니다.

**결과.** 2,000판씩 측정했습니다.

| 버전 | 팀 0 승률 | 골 |
|---|---|---|
| 기존 | 47.1% | 2.00 · 2.14 |
| (1)만 | 44.0% | 1.96 · 2.17 |
| (1)+(2) | 47.2% | 2.01 · 2.10 |
| (1)+(3) | 45.0% | 1.82 · 1.99 |
| **셋 다** | **50.5%** | 1.91 · 1.91 |

**배운 것 두 가지.** 하나는 **"22명을 인덱스 순으로 돈다"는 결정론을 위한 규칙이지 공정성을 주지 않는다**는 것입니다.
다른 하나는 **부분 수정이 더 나쁠 수 있다**는 것입니다 — (1)만 고치면 44%로 오히려 악화됐습니다. 세 개가 서로 기대고 있었습니다.

마지막으로, 통계는 유닛 테스트로 못 잡으니 **구조를 지키는 테스트**를 넣었습니다: "결정 시점에 아무도 움직이지 않았다", "공 가진 팀이 먼저 결정한다", "주기는 자리 번호로". 이 테스트는 옛 코드에서 실패합니다.

> **"다른 사례도 있나요?"**

**부호 하나가 규칙을 통째로 뒤집은 적**이 있습니다. "골키퍼와 1대1인 공격수를 뒤에서 태클로 뺏는다"는 제보를 받고 보니,
"뒤에서 들어왔는가"를 판정하는 함수가 처음부터 **뒤집혀** 있었습니다. 도전자가 소유자 **앞**에 있을 때 1(등 뒤)을 돌려주고 있었습니다.
그래서 정면 도전이 파울로, 뒤 도전이 정면으로 취급됐습니다. 각도·방향 함수는 **정면/뒤 두 케이스 단위 테스트를 같이 넣는다**가 그때 규칙이 됐습니다.

고친 뒤에 새 문제가 생긴 것도 이야깃거리입니다. 뒤 태클을 카드로 만들자 **봇끼리 퇴장이 판당 2.3회**가 났습니다.
규칙을 세게 만들면 **AI가 먼저 그 규칙을 지켜야** 합니다. 그래서 봇은 아예 뒤에서 덤비지 않고 골사이드로 앞지르게 하고, 사람만 위험을 감수하고 도전할 수 있게 했습니다.

## 7. 경제·시스템 설계

> **"뽑기가 없는데 어떻게 스쿼드에 선택의 여지를 만들었습니까?"**

카드 1,056장을 처음부터 전부 열고 **급여 상한** 하나로 조였습니다. 그런데 상한 하나로는 두 가지 일을 못 시킵니다.

- 약한 구단도 자기 선수 18명으로 팀을 짤 수 있어야 하니 상한이 낮으면 안 됩니다.
- 그런데 그만큼 높으면 누구나 올스타 선발을 살 수 있습니다.

실측해 보니 제한이 없을 때 **29개 구단 전부 최강 선발이 OVR 92~94로 수렴**했습니다. 어느 구단을 골라도 같은 팀이 된다는 뜻입니다.
그래서 **다른 축**을 만들었습니다.

| 장치 | 막는 것 | 효과 |
|---|---|---|
| 영입 인원 제한(선발 5·후보 2) | 올스타 팀 | 구단 간 격차 8.1 → 11.4 |
| 영입 웃돈 ×1.5 | 상한이 헐거운 것 | 상한 사용률 186 → 224/252 |
| 약체 가산(팀워크) | 약팀이 못 따라가는 것 | 최저 구단 62.8 → 77.6 |

**"상한 하나로 두 가지 일을 시킬 수 없다"** 가 여기서 얻은 교훈입니다.

> **"최근에 사용자 피드백으로 바꾼 게 있습니까?"**

"강한 팀은 자기 선수 급여만으로 상한이 거의 차서 영입을 못 한다"는 질문을 받았습니다.
재 보니 사실이었습니다(울산 239/252). 그런데 이 게임엔 **돈 개념이 없어서 '판다'는 절차 자체가 없습니다** — 스쿼드에서 빼면 급여가 그대로 돌아옵니다.
문제는 그걸 아무도 모른다는 것이었고, 상한을 낮추면 약팀이 팀을 못 짭니다. 그래서 **그 한 걸음을 버튼으로** 만들었습니다:
후보 7명을 자기 구단에서 가장 싼 선수로 바꾸는 버튼(239 → 211), 고른 자리 하나만 싼 선수로 바꾸는 버튼, 그리고 급여 게이지에 "빼면 급여가 돌아옵니다" 문구.

**밸런스를 바꾸는 대신 이해를 바꾼 사례**입니다.

## 8. 성능

> **"성능 예산이 있습니까?"**

틱당 **0.5ms 이하**(22명 AI 포함)를 예산으로 정하고 `tests/perf.test.ts`가 매번 잽니다. 현재 **0.094ms** 입니다.

주로 이렇게 벌었습니다.

- AI 결정 주기를 15틱으로 분산 — 한 틱에 두 명만 다시 결정합니다.
- 할당을 피합니다. 매 틱 쓰는 임시 좌표 객체는 모듈 스코프에 재사용 객체를 둡니다.
- 렌더는 prev/curr **보간**만 합니다. 60Hz 틱과 화면 주사율이 달라도 부드럽고, 시뮬을 다시 돌리지 않습니다.

렌더 쪽은 그림자·해상도 배율을 설정으로 빼서 저사양 PC에서 끌 수 있게 했습니다.

## 9. 오디오

> **"소리는 어떻게 만들었습니까?"**

**음원 파일이 하나도 없습니다.** 전부 Web Audio로 절차 생성합니다 — 킥·휘슬·관중·배경음악까지 오실레이터와 노이즈뿐입니다.
저작권 문제가 없고 번들도 가볍습니다.

관중은 층으로 쌓았습니다: 웅성거림(필터 건 노이즈) + 함성 층(목소리 대역, **공이 골문에 가까울수록 제곱으로** 올라옴) + 느린 숨쉬기 LFO + 흩어지는 박수·휘파람·탄성 + 주기적으로 돌아오는 응원가.
"소리만 듣고도 위험한 장면인지 알 수 있어야 한다"가 기준이었습니다.

> **"중계 음성(TTS)은 어떻게 붙였습니까?"**

브라우저 내장 `speechSynthesis`만 씁니다. 결정적인 이유는 **선수 1,056명의 이름을 미리 녹음할 수 없다**는 것이었습니다.
외부 TTS API는 키·요금·네트워크가 붙고, 운영체제 음성은 공짜·오프라인이며 이름을 그대로 읽습니다.

설계에서 신경 쓴 부분은 세 가지입니다.

1. **하이라이트만 말한다** — 골·PK·퇴장·선방·골대·전후반 시작/종료. 파울·슛·태클은 판당 10번이 넘어 제외했습니다. 계속 떠들면 금방 거슬립니다.
2. **겹치지 않게** — 급을 3단계로 나눠 골은 하던 말을 끊고, 곁들이는 말은 9초 이상 조용할 때만 합니다.
3. **탭이 숨겨지면 말하지 않는다** — 브라우저가 큐에 쌓아 뒀다가 돌아올 때 한꺼번에 터집니다.

남성 음성이 요구사항이었는데 테스트 PC에는 한국어 여성 음성 하나뿐이었습니다. 그래서 **남성 음성이 있으면 고르고, 없으면 피치를 낮춰 읽고**, 설정 화면에 지금 무슨 음성인지와 남성 음성을 받는 방법을 띄웠습니다.

## 10. 테스트·품질

> **"테스트는 어떻게 짰습니까?"**

167개이고, **버그를 재현 테스트로 못 박는** 방식입니다. 제보를 받으면 먼저 실패하는 테스트를 만들고 고칩니다.

대표적으로:

- **결정론** — 같은 시드 두 번, 60틱마다 해시 전부 비교
- **성능** — 틱당 0.5ms 예산
- **배선** — "원정을 맡으면 선수가 안 움직인다"는 제보의 원인은 입력을 0번 칸에 고정한 한 줄이었습니다. 배선을 순수 함수(`soloInputs`)로 빼니 테스트가 잡습니다
- **방향 함수** — 뒤 태클 판정은 정면/뒤 두 케이스를 모두 봅니다
- **구조** — 위에서 말한 결정 순서 세 성질
- **데이터** — 장수를 못 박지 않고(명단은 바뀝니다) "구단 29개, 구단마다 18명 이상 + GK 1명 이상, id 중복 없음, id가 11비트 안"을 봅니다

> **"CI는요?"**

GitHub Actions가 푸시마다 `tsc --noEmit` + `vitest` + `vite build`를 돌리고 Pages로 배포합니다. 빌드가 깨지면 배포가 안 됩니다.

## 11. 협업·기록

> **"혼자 한 프로젝트인데 문서를 왜 이렇게 많이 썼습니까?"**

세션이 끊겨도 이어서 할 수 있어야 했고, PC 두 대를 오가며 작업했기 때문입니다. 네 종류로 나눴습니다.

| 문서 | 역할 |
|---|---|
| `DESIGN.md` | 설계 정본 — 규칙·수식·검증 기준 |

| `HANDOVER.md` | 현재 상태·다음 할 일·**실패 기록** |

특히 `HANDOVER.md`의 **"실패했거나 되돌린 것"** 표가 값어치가 컸습니다.
"속도 폭만 줄였다 → 81%, 여전히 지배적", "대칭을 200판으로 판정 → 노이즈에 속았다" 같은 것을 적어 두면 같은 실수를 두 번 안 합니다.

## 12. 한계와 다음 단계

> **"이 프로젝트의 한계는 뭡니까?"**

정직하게 말하면 세 가지입니다.

1. **NAT 통과** — TURN이 없어 대칭 NAT에서는 붙지 않습니다. 서버 0대 원칙과 맞바꾼 결과입니다.
2. **2인 전용** — 락스텝은 인원이 늘수록 지연이 최악값을 따라가서, 관전·4인은 구조를 바꿔야 합니다.
3. **사람 체감은 아직 표본이 적다** — 봇 계측은 수천 판이지만, 실제 사람 대전은 로컬 두 탭까지만 확인했습니다. 다른 회선 두 대 테스트가 남아 있습니다.

> **"더 한다면 뭘 하겠습니까?"**

- **강화 시스템이 값을 하게** — 현재 능력치 +24를 다 써도 승률 +2~3%p뿐입니다. 곱셈 스킬식에 묻히는 구조라 계산 위치를 바꿔야 합니다(목표 8~15%p).
- **재접속·리싱크 강화** — 지금은 스냅샷 되돌리기뿐이라 긴 끊김에 약합니다.
- **관전 모드** — 입력만 흐르므로 원리적으로는 제3자가 같은 입력 스트림을 받아 그리기만 하면 됩니다.

## 13. 짧게 답할 질문 모음

> **"가장 자신 있는 코드는?"**

`fixedmath.ts`입니다. 40줄짜리 룩업 테이블과 이진 탐색 `atan2`인데, 이게 없으면 P2P 동기화 전체가 성립하지 않습니다. 제약을 이해하고 고른 가장 작은 해법이라고 생각합니다.

> **"다시 한다면 뭘 다르게 하겠습니까?"**

계측 도구를 **더 일찍** 만들겠습니다. 능력치가 경기에 안 닿는다는 걸 A/B로 알기 전까지는 감으로 계수를 만지고 있었고, 그 기간이 가장 비효율적이었습니다.
또 `step()`처럼 순서가 중요한 함수는 처음부터 **단계를 나눠서** 짜겠습니다. 결정과 이동이 한 루프에 섞여 있던 게 3%p 편향의 뿌리였습니다.

> **"AI 도구를 썼습니까?"**

네. 설계 판단과 우선순위는 제가 정하고, 구현과 계측 도구 작성에 적극적으로 썼습니다.
중요한 건 **결과를 숫자로 검증하는 습관**이었습니다 — 생성된 코드든 직접 쓴 코드든 "능력치가 반영되나", "대칭이 맞나"는 결국 수천 판을 돌려 확인해야 했습니다.

> **"이 프로젝트에서 얻은 가장 큰 교훈은?"**

**"느낌으로 판정하지 않는다."** 홈 41%도, 능력치가 안 닿던 것도, 속도가 지배적이던 것도 전부 눈으로는 안 보였고 숫자로만 보였습니다.
그리고 그 숫자도 **표본이 모자라면 거짓말을 합니다**.
